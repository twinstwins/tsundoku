# Tsundokuのフロントエンド移行計画

既存の利用者操作をE2Eテストで確認できる状態にしてから、Railsの認証とデータを使いながら、画面をReactとTypeScriptへ段階的に移す。ビルドにはViteを採用する。Bunを比較検証した結果、今回の移行ではNode.js 24とnpmを継続する。最初の画面はユーザー一覧と投稿詳細とし、更新系の操作と認証画面を後から移行する。

## 現状と進捗

現状はRuby 2.5.1、Rails 5.2、ERB、Sprockets、Bootstrap 4、jQuery、Rails UJS、Turbolinksで構成される。旧画面の操作はRails UJSを継続し、Reactの投稿詳細のいいね・コメントと、プロフィールのフォローはJSON APIへ移行した。ユーザー一覧・ログイン済みの投稿詳細・公開プロフィールはReact・TypeScript・ViteとCSS Modulesへ移行し、依存は`frontend/`に分離した。API契約・OpenAPI・生成型を使う。既定はERBで、画面別の設定により切り替える。いいね・コメント・フォローも独立した設定を持つ。本人の編集導線はReact領域の外に残す。投稿APIのログイン必須を維持し、ゲストの投稿詳細HTMLは従来の公開ERBを使う。

第0段階ではPlaywrightとTypeScript、専用Compose環境、GitHub Actionsを導入した。続く第1段階では認可・入力検証と読み取りAPI・生成型を追加した。第1.5段階のBun比較も実施し、Node.jsとnpmの継続を判断した。PCとモバイルのChromiumで、次の12シナリオ（計24ケース）を実行する。

| 分野 | E2Eで確認する操作 |
| --- | --- |
| 認証 | ゲスト表示と誤ったパスワード、新規登録からログアウト・再ログイン、アバター付き登録 |
| プロフィール | 現在のパスワードを使った名前・アバターの更新 |
| 投稿 | 画像なし投稿の詳細、画像投稿とサムネイル、共有投稿と保存後の画面遷移 |
| ソーシャル | いいねと取消、コメント作成と本人による削除、フォローと解除・双方の一覧 |
| API | 公開項目と未認証拒否、本人情報・CSRF・他人の更新拒否 |

ブラウザーのCookieはテストごとに分離し、ユーザー名・メールアドレスは毎回生成する。DBとアップロード先は専用コンテナ内に置く。通常の開発DBや既存のアップロード画像を書き換える構成にしない。専用環境の既定値はdevelopmentとし、CIではproduction設定とビルド済み成果物を使う。どちらもCSRF保護と実際のJavaScriptによる操作を確認する。

テストは実際の登録・入力・クリックを使う。表示名とラベルを優先し、繰り返し表示される投稿だけ共通の`data-testid`で識別する。RailsのCSSクラスやDOM階層にテストを結び付けず、React側にも同じ操作上の識別子を引き継ぐ。[Playwrightの推奨方針](https://playwright.dev/docs/best-practices)

認可・入力不正・CSRFはrequest specとAPIのE2Eで確認する。パスワード再設定、アカウント削除は後続で追加する。3画面・いいね・コメント・フォローの新旧設定で、新画面102件・既存画面50件、開発時更新2件を確認する。いいね・コメント・フォローの同時送信、応答消失後の実状態確認、CSRF再取得、オフライン復帰と再ログイン後に自動再送しないことも扱う。コメントの下書き保持、ページ送り、本人だけの削除も確認する。部品テストは61件。この範囲を「全機能の保証」とは扱わない。

### Bunの検証と採用判断

第1.5段階の独立したPRでBun 1.4.4とNode.js 24.22.1を比較し、今回はNode.jsとnpmを継続すると判断した。Bunで依存を導入する構成は動作したが、Bunでの実行ではPlaywrightがテストの読み込みで失敗した。依存管理だけの変更は短縮幅が小さく、現段階で導入する利点が十分ではない。反復測定と判断の詳細は[Bunの検証結果](bun-evaluation.md)を参照する。次回の再評価も[Bun公式のVite案内](https://bun.sh/guides/ecosystem/vite)を参照し、次の二段階を分けて評価する。

1. 依存管理にBunを使用し、Vite・型チェック・PlaywrightはNode.jsで実行する。
2. Vite・型チェック・Playwright自体もBunで実行する。実行コマンドとランタイムのバージョンをログに残し、CLIの指定によりNode.jsが使われる場合と区別する。E2Eの実行器はPlaywrightを継続する。

今回、既存E2Eと型生成・型チェックに加え、最小React・ViteサンプルのHMR、React Refresh、本番ビルド、Railsからのmanifest読込とJS・CSSの実際の配信を確認した。次の画面移行用の基盤には検証済みのNode・Vite構成を反映する。再評価時にも次の条件を用いる。

| 検証対象 | 確認内容 |
| --- | --- |
| 依存関係 | 同じパッケージ版を解決でき、固定したBunとlockfileでクリーンインストールを再現できる。必要なインストールスクリプトとネイティブ依存も確認する |
| 機能互換 | 同じ型生成・型チェック・PCとモバイルのE2E24ケース・最小React/Viteサンプルが成功し、再試行による成功に依存しない |
| CIと開発環境 | 固定ブラウザーコンテナに固定版Bunを追加し、GitHub ActionsのLinuxと開発用macOSで実行する。失敗時のレポート保存と終了コードも確認する |
| 実行時間 | 同じマシン・コード・依存バージョンで、キャッシュなし／ありを分けて各5回測定する。依存導入、開発サーバー起動、本番ビルド、E2EとCI全体の中央値・ばらつきを比較する |
| 運用 | lockfile更新、依存アップデート、バージョン固定、障害時の調査とNode.jsへの復帰に必要な手順を確認する |

次回の再評価でも機能互換と再現性を必須条件とし、時間短縮や運用上の利点を実測で示せる範囲を採用する。結論は「依存管理と実行環境の両方に採用」「依存管理だけ採用」「Node.jsとnpmを継続」のいずれかとし、測定結果と判断理由を計画書に追記する。互換性の問題や維持が難しい回避策が残る場合は、Node.jsとnpmを継続する。

採用した場合はCI成功後にlockfileを一本化する。Bunへの変更を独立したPRにまとめ、問題が出た場合はその変更を戻して検証済みのNode.jsとnpmの構成へ復帰できるようにする。

### JSON APIより先に整える処理

第1段階で、利用者の権限と必須入力をサーバーで検証する処理を追加した。読み取りAPIの契約と生成手順は[APIの利用手順](api/v1/README.md)を参照する。更新APIを増やす際にも次の制約を維持する。

- プロフィール更新はログイン本人のレコードに限定する。
- コメントの作成者は`current_user`から決める。コメントといいねの削除は本人の関連から検索する。
- 未認証アクセス、存在しない投稿、必須項目の不足を例外任せにしない。ユーザーに表示するエラー形式を決める。
- 同じ投稿へのコメントは既存の1ユーザー1件を維持し、空欄と重複を拒否する。今回の更新APIでも同じ制約を維持する。
- 共有投稿で画像も引き継ぐかを決める。現状のフォームにある画像URL入力を、そのまま新APIの仕様にはしない。

APIは`/api/v1`に設け、既存のHTML・JavaScript応答と併存する。第1段階では読み取りを整備し、第4段階でいいねのPUT・DELETEを追加した。同じ要求の繰り返しでも状態を反転させず、新旧書き込みを投稿行のロックで揃える。JSONのフィールド、ページング、画像URL、エラー形式をOpenAPIで定義し、TypeScript型を生成してCIで差分を検出する。コメントのGET・POST・本人によるDELETEも追加し、1ユーザー1投稿1件と新旧書き込みのロックを維持した。フォローもログイン必須の状態GETと冪等なPUT・DELETEを追加し、公開APIに本人の状態を混ぜず、既存の一意制約と新旧画面からの書き込みのロックを維持した。

### 認証と画面を共存させる条件

APIはRailsと同じオリジンで提供する。ReactはセッションCookieを送り、更新リクエストにRailsのCSRFトークンを付ける。APIの未認証応答はJSONの401とし、ログイン画面への移動と復帰先は画面側で扱う。

Reactのルート要素の内側はReactが更新する。既存jQueryの置換先や`data-remote`をReact要素へ重複して持ち込まない。移行画面ではTurbolinksの画面キャッシュとReactのマウント・破棄を明示的に管理する。新CSSのグローバルリセットを既存ERB画面へ適用しない。

## Railsとデータの更新

E2E・ViteのJavaScript実行環境は、現在のRails実行環境と別コンテナで動かす。今回の比較結果に基づき、実行環境はNode.js 24とnpmを継続する。これにより、Rails更新中もフロントの準備を進められる。新しいバックエンドを公開する段階では、Ruby・Rails・MySQLをサポート対象の組合せへ更新する。

RubyとRailsの更新は、対応するRuby版を挟みながらRailsのマイナー版ごとにPRを分ける。各段階でRSpecと同じE2Eを実行する。Devise、CarrierWave、画像処理、Cookie形式、DBアダプターを重点確認する。中間版は移行作業用とし、リリース先の最終構成とは区別する。[Rails公式の更新手順](https://guides.rubyonrails.org/upgrading_ruby_on_rails.html)

`vendor/bundle`と`mysql/mysql_data`には現在Git追跡中の実行時ファイルがある。実データの有無とバックアップを確認してから、依存管理とDBボリュームへ移す。DB更新は実データのコピーで復元を検証する。フロント移行のPRでは、既存カラムやアップロード画像を削除しない。

## リリース判定と切り戻し

- 画面単位のサーバー設定で、ERBとReactを切り替えられるようにする。初期値はERBとし、移行した画面から有効にする。
- 各画面を旧・新の両設定でE2Eに通す。APIの認可はRSpecで確認し、ブラウザーではセッション切れや送信失敗からの復帰も確認する。
- Reactの部品・フォームはVitestとReact Testing Libraryで確認する。E2Eは利用者が完了できる操作を確認し、すべての入力組合せをE2Eへ集めない。
- PRではPC・モバイルChromiumを必須にし、移行開始に合わせてFirefoxとWebKitを含む定期実行を追加した。失敗をリトライで隠さず、再試行でのみ成功した場合もCIを失敗にする。
- CIの全体15分以内、E2E本体5分以内を目標にし、実測で調整する。失敗時のトレース・画像・動画とRailsログを7日間保持する。
- 切り戻しは対象画面の設定をERBへ戻す。旧画面が必要とするAPI・JSと、直前リリースのVite成果物を残す。データ変更は追加から始め、旧画面に戻せる期間を確保する。
- 500、認証・更新操作の失敗、二重送信、画像欠落が増えた場合は対象画面を戻し、同じE2Eへ再現ケースを追加する。許容値はリリース前に既存画面の実測と比較して定める。

3画面・いいね・コメント・フォローの起動・有効化・切り戻し・検証は[Reactフロントの手順](react-frontend.md)を参照する。次のPRは第5段階の投稿フォームのAPIとReact移行とする。本文と画像の入力、422の項目別表示、入力保持、二重投稿の防止、保存後の画面遷移、セッション切れからの復帰を確認する。その後、共有・プロフィール・認証フォームへ進む。
